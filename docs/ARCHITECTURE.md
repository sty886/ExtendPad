# Architecture

ExtendPad connects a sending Mac to Android and Mac receivers. The Mac always
captures and sends video/audio; receivers can request permission to send input
back over the authenticated session.

```text
Mac sender                                  Android or Mac receiver
ScreenCaptureKit                            TLS listener
Virtual display / existing display          Pairing and session admission
Video/audio encoders       encrypted media  Decoders and presenters
Input injection           ◀───────────────  Approved input events
```

## Targets and modules

Defined in `project.yml`; the `.xcodeproj` is generated by XcodeGen.

| Target/module | Sources | Role |
| --- | --- | --- |
| `OpenSidecarMac` | `apps/macos/`, `packages/shared/`, selected `apps/macos-receiver/` | Mac sharing plus the unified receiver role |
| `OpenSidecarMacReceiver` | `apps/macos-receiver/`, `packages/shared/`, selected Mac utilities | Standalone macOS 12+ receiver |
| `OpenSidecarMacTests` | `tests/macos/` and selected production sources | Hostless Mac tests |
| Android `core` | `apps/android/core/` | Kotlin/JVM protocol and receiver logic |
| Android `app` | `apps/android/app/` | Android integration and Compose UI |

## Mac sender

- Session and device lifecycle: `apps/macos/OpenSidecarMacApp.swift`
- Capture, encode, transport and input: `apps/macos/MacSender.swift`
- Capture lifecycle: `apps/macos/CaptureLifecycle.swift`
- Virtual display isolation: `apps/macos/VirtualDisplay.swift`
- Display assignment: `apps/macos/DisplayModeAssignment.swift`
- Input authorization and injection: `apps/macos/InputControlConsent.swift`,
  `apps/macos/InputInjector.swift`, `apps/macos/InputRouting.swift`
- Android USB: `apps/macos/AndroidUSB.swift` and
  `apps/macos/USBTLSBridge.swift` (authorized ADB tunnel; the Android side
  also carries the AOA accessory channel for devices/firmware that complete
  the accessory switch — see TECHNICAL_NOTES.md)
- Network transport: `apps/macos/MacSenderTransportController.swift`

Android USB uses an authorized ADB tunnel as opaque bytes on the shipping
path; Android also declares an AOA accessory control channel for devices
that complete the switch. AOA/ADB never grant trust: the normal pairing,
pinned identity and encrypted session still apply.

## Shared Swift code

`packages/shared/` contains the receiver core and platform-neutral logic:

- `StreamReceiver.swift`: listener, session and control dispatch
- `ReceiverPipelineActor.swift`: receive pipeline ownership
- `ReceiverVideoDecoder.swift` and `ReceiverAudioDecoder.swift`: decoding
- `Protocol.swift`: wire messages and capabilities
- `Pairing.swift`, `PairingNetwork.swift`, `TrustStore.swift` and
  `TLSConfigurator.swift`: pairing and trust
- `SessionInvitation.swift`: admission and approval
- `PointerGestureEngine.swift`, `RemoteViewport.swift` and control models:
  input interpretation and receiver-local presentation

Pure logic remains platform-neutral so `tests/macos/` can exercise it without
an app host.

## Android

`apps/android/core/` implements the protocol in Kotlin and replays shared
fixtures from `fixtures/`. `apps/android/app/` integrates Android Keystore,
DNS-SD, MediaCodec, Compose, input, USB and device-adaptive UI.

## Mac Receiver

`apps/macos-receiver/` provides the AppKit shell, video window, settings,
pairing UI and keyboard/trackpad forwarding. The main Mac target reuses most
of it while excluding the standalone entry point and bundle resources.

## Security and lifecycle invariants

- No plaintext media fallback or route-based identity substitution.
- Connection approval never implies input approval.
- Every connection re-earns admission and input permission.
- Capture lifecycle stays separate from transport recovery.
- Only the intended session owns capture and input injection state.
- Protocol changes follow [COMPATIBILITY.md](COMPATIBILITY.md) and
  [PROTOCOL.md](PROTOCOL.md).
- `project.yml` is the build source of truth.
